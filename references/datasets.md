# Bundled example datasets

Five synthetic fixtures live in `examples/data/`, generated by `examples/make_datasets.py` and exercised by
`tests/test_example_*.py`. They exist so every guard in this skill is demonstrated on a real file instead of
being asserted in prose: each one plants a specific pathology, and a test proves the corresponding check fires.

Why synthetic and not scraped data:

- **Legal and ethical.** No personal data, no scraped listings, no customer records in a public repo.
- **Reviewable pathology.** The leak is a documented line in the generator, not a rumour about a column.
- **Deterministic.** Fixed seeds, no clock, no network. `python examples/make_datasets.py --check` proves the
  committed CSVs still reproduce byte-for-byte.

They are fixtures, **not a benchmark**. Never quote a model score from them as a result.

**The set is closed at five.** They cover the pathologies this skill is about, and repo size is part of the
product: a clone is a skill install, not a data download. A sixth dataset needs an issue arguing which guard the
existing five cannot demonstrate (`tests/test_example_datasets.py::test_fixture_set_is_frozen_at_five` enforces
the count). Improvements belong in `references/playbooks.md`, `references/stats-recipes.md` or `scripts/dstk/`.

## churn_leaky.csv

Classification with **repeated entities** (1–3 snapshots per customer). A random split would put the same
customer on both sides, and two columns are recorded after the outcome:

- `support_calls_after_cancel` — support contacts logged after the cancellation. AUC ≈ 0.98 on its own.
- `cancelled_at` — a timestamp that exists exactly for churners. As a boolean it is AUC = 1.00.

The honest feature set (`tenure_months`, `monthly_spend`, `plan`, `region`, `support_calls_90d`) reaches
AUC ≈ 0.63 on a grouped split. Adding the two leaks takes it to ≈ 0.99. That 0.36 gap is the most useful
number in the fixture: it is what a leak buys you, and no algorithm can be blamed for losing it.

Around 5% of `monthly_spend` is missing, so imputation must live inside the pipeline.

## sales_daily.csv

2024-01-01 to 2025-12-31, daily, with a weekly profile (Friday/Saturday peak), a mild upward trend, 5% promo
days and noise. Use it to practise:

- refusing a random split (`assert_temporal_order` rejects it);
- expanding-window backtests (`rolling_origin_splits`: three 30-day windows);
- the baseline ladder: seasonal-naive (season 7) beats plain naive in every window;
- the MASE trap: the **scale** comes from the seasonal-naive in-sample error and must be the same for every
  forecast being compared. Recomputing it per forecast (season 1 for one, season 7 for another) silently
  changes the benchmark and can flip the answer.

## listings_ar.csv

150 properties, 200 listing rows: ~30% were re-listed with an edited title (Arabic-Indic digits, `م٢` vs `م2`,
extra punctuation and spaces) and a price change of up to ~4%. No two rows are identical, so a row-duplicate
check finds nothing while a random split still puts the same property on both sides.

`dstk.leakage.normalize_text` maps the variants to one string; `text_group_ids` turns them into a group key;
`row_overlap` shows the leak before and after. Titles are unique per property by construction, so a group
means "this property was re-listed" — which is exactly the claim the test makes.

## experiment_ab.csv

2,000 users per arm, 50/50, verified by `srm_check`. Conversion 8.05% → 10.30% (+2.25pp, 95% CI
[+0.46pp, +4.04pp], p ≈ 0.014). The interesting parts:

- **`support_tickets` is a guardrail that moves the wrong way** (≈ +27% per user). A review that reports only
  conversion is incomplete.
- **`pre_spend` is a pre-period covariate**: CUPED on `week1_minutes` cuts variance by ~75% without moving the
  point estimate, which is the entire reason to use it.
- **Power**: 80% power would have needed ~2,600 users per arm; the fixture has 2,000. The p-value is still
  < 0.05, which is precisely why an under-powered win is "promising", not "settled".

## interactions.csv

260 users × 96 items × ~12 events, generated from 8 latent topics (users consume 1–2 topics). Use it to
practise ranking evaluation:

- `leave_last_out` keeps every user's future out of training;
- **popularity is not automatically better than random** here (NDCG@10 ≈ 0.043 vs 0.054), because the popular
  items are the ones everyone already saw. Measure your baselines, do not assume their order;
- item-item CF reaches NDCG@10 ≈ 0.35 with non-overlapping intervals, which is the claim a ranking report
  should make: same users, same k, paired comparison.

## Regenerate or verify

```bash
python examples/make_datasets.py           # rewrite examples/data/*.csv
python examples/make_datasets.py --check   # fail if a committed CSV no longer matches the generator
pytest tests/test_example_*.py             # run the guards on the fixtures
```

`tests/test_example_datasets.py` also fails when a CSV is edited by hand. If you intentionally change a
fixture, regenerate and review the diff — the same discipline this skill asks of `results.json`.

## Use a fixture as your own project hook

Copy `examples/project_hooks_example.py` and point it at one of these files: `get_split()` must declare the
grain (`group_col` for repeated entities, `time_col` + `temporal_split` for the series), and every hook-based
test in `tests/` then runs against your project instead of the housing example.
